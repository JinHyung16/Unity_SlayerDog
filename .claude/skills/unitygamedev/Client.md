# Client — 부트 · 시스템 · 수명주기 · 검증

> 성능 기법은 `Optimize.md`, 데이터는 `DataFramework.md`, UI 는 `UIFramework.md`.
> 여기는 **엔진을 어떻게 세우고 어떻게 재는가**다.

## 이 역할이 지키는 것

클라의 완료 조건은 「구현했다」가 아니라 **「실측 숫자가 스펙 기대값과 맞았다」**다.
그래서 클라는 기능과 **하네스를 같이** 만든다. 하네스 없는 기능은 미완이다.

---

## 최소 세트 — 처음부터 다 만들지 않는다

프레임워크를 미리 다 만들면 대부분 안 쓰인다. **슬라이스가 요구하는 것만** 세운다.

```
[예시] 슬라이스에 필요한 최소 세트
GameInitialize   부트 순서의 «유일한» 출처
<X>Manager       전역 서비스 (풀 · 로드 · 오디오 · 세이브 · 데이터)
<X>Management    화면/흐름 단위 진행 (UI 창 관리 · 씬 흐름)
GameFlow         런의 시작/종료 상태 (정적, 리셋 진입점 포함)
Harness          검증 하네스 + 워치독
```

**공용으로 올리는 기준은 「두 번째 사용처」다.** 한 곳에서만 쓰는 것을 Common 에 올리면
그 Common 은 곧 아무도 못 고치는 폴더가 된다.

## 두 갈래 — Manager 와 Management

| | Manager | Management |
|---|---|---|
| 무엇 | 전역 서비스. 상태를 들고 산다 | 흐름/화면의 진행. 서비스를 «쓴다» |
| 수명 | 앱 전체 | 씬/화면 |
| 예 | Pool · Loader · Audio · Save · DataRegistry | UI 창 관리 · 씬 전환 · 튜토리얼 진행 |

**호출 방향은 한쪽이다: Management → Manager.**
Manager 가 Management 를 부르기 시작하면 순환이 생기고, 그때부터 초기화 순서를 못 잡는다.
Manager 가 위로 알려야 하면 **이벤트**로 던진다.

## `GameInitialize` — 순서의 유일한 출처

초기화 순서를 각자의 `Awake` 에 흩어 두면 **순서가 우연이 된다.**
한 진입점이 정해진 순서로 세운다.

```
[예시] 순서
1. 설정 적용 (해상도 · 프레임 상한 · 색공간 확인)
2. 저장 데이터 로드 (여기서 실패하면 아래가 전부 의미 없다)
3. 데이터 Registry 로드 + 검증
4. Manager 생성 (Pool · Loader · Audio …)
5. Management 생성
6. 첫 화면 진입
```

- **비동기 초기화가 나중에 돌며 앞의 결과를 지우지 않게** 한다.
  [사고] 비동기 로드가 뒤늦게 끝나며 이미 장착된 것을 초기값으로 덮었다.
  → 각 단계의 완료를 «기다리고» 다음으로 간다. 순서가 규약인 이유가 이것이다
- 씬 리로드 경로에서도 같은 순서가 보장되는지 확인한다. 정적 상태는 **명시적 리셋 진입점**을 둔다

## `GameFlow` — 런의 상태는 한 곳에 산다

- 런의 시작/종료/일시정지 상태를 정적으로 들고, **이벤트로 알린다**
- `timeScale` 을 만지는 곳을 한 곳으로 모은다 — 여러 곳에서 만지면 누가 0으로 뒀는지 못 찾는다
- **씬 리로드 직전에 런 상태를 지우는 경로**를 만든다. 부트 훅은 앱 시작에 한 번만 돈다

## 무작위는 한 곳에서만 꺼낸다

- 게임플레이 난수는 **시드를 들고 있는 하나의 소스**에서만 꺼낸다
- 시드 고정 = 리플레이 = 밸런스 실측 가능. 흩어진 `Random` 은 재현을 불가능하게 만든다
- 연출용 난수와 게임플레이 난수를 분리한다 (연출이 판정 결과를 바꾸면 안 된다)
- 점검법: 엔진 난수 API 호출을 grep 해서 소스 밖 호출이 0인지 센다

## Unity 수명주기 — 조용히 망가지는 자리들

| 자리 | 규칙 |
|---|---|
| Awake/OnEnable/Start 순서 | 참조 캐시는 Awake, 이벤트 구독은 OnEnable(+OnDisable 해제), 외부 의존 초기화는 Start |
| 정적 이벤트 | 구독한 쪽이 해제 책임. 씬 리로드 시 정적 상태를 리셋하는 진입점을 둔다 |
| `[InitializeOnLoad]`/정적 생성자 | **도메인 리로드 때만 돈다.** 상시 감시는 `EditorApplication.update` 에 |
| 에디터 자동화 | 에디터는 포커스 받을 때만 임포트한다 — 자동화 훅은 `AssetDatabase.Refresh()` 를 직접 부른다 |
| 백그라운드 | 백그라운드에서 게임 루프가 멈춘다 — 자동 검증엔 `runInBackground` 필수 |
| 도메인 리로드 | 새로 고침 직후 플레이 진입은 자동화를 먹는다 — 컴파일 완료를 기다리고 들어간다 |

풀링 계약(3법칙)·핫패스 무할당·중앙 틱은 `Optimize.md` 「처음부터 넣는 것」에 있다.

## 값의 채널 — 쓰는 쪽과 읽는 쪽을 반드시 잇는다

[사고] 디버프가 `A.SpeedMultiplier` 에 값을 곱했는데 이동 코드는 `B.SpeedMultiplier` 를
읽고 있었다. 컴파일·로드 전부 통과, 런타임 무동작.

**새 수치 채널을 만들면 그 자리에서 소비처를 grep 으로 확인한다** — 소비처 0이면 죽은 채널이다.

같은 채널을 여러 주체가 쓸 때(AI 가 매 틱 덮어쓰는 배수 vs 상태이상이 곱하는 배수)는
**채널을 분리**한다. 한 채널에 섞으면 나중에 쓴 쪽이 이긴다.

## 판정 로직은 한 경로로 모은다

[사고] 팀 판정(아군/적)을 호출처마다 흩어 뒀더니, 새 공격 경로가 생길 때마다 아군 오사가 재발했다.
**피해·적중·팀 판정 같은 규칙은 함수 하나를 거치게 하고**, 새 경로는 그 함수를 부르게 한다.
grep 으로 「그 함수를 안 거치는 피해 적용」이 0인지 셀 수 있어야 한다.

## 씬·물리 최소 체크리스트

- [ ] 지면·벽에 **콜라이더가 있다** ([사고] 렌더러만 있는 지면 — 전원 낙하)
- [ ] `timeScale=0` 게이트가 어디에 있는지 파악했다 — 자동화가 여기 걸린다
- [ ] 카메라가 씬에 하나뿐인지 / UI 카메라 분리 여부 (`View.md`)
- [ ] 입력이 인터페이스로 추상화됐다 (`Platform.md`)
- [ ] 씬 리로드(재시작) 경로에서 정적 상태·풀·이벤트가 전부 리셋된다
- [ ] 물리 기반 이동과 커스텀 이동을 **섞지 않았다** (섞으면 경계에서 반드시 샌다)

## 검증 하네스 문화

- 하네스는 요청 파일/메뉴로 **사람 개입 없이** 돈다: 플레이 진입 → 시나리오 실행 →
  숫자 리포트 + 스크린샷 → 종료
- **워치독 필수**: 경과 프레임·게임 시간을 리포트에 병기하고, 시간이 흐르지 않으면
  결과 대신 「무효」를 보고한다. [사고] 멈춘 게임에서 「피해 0」이 정상처럼 보고됐다
- 측정 오염을 격리한다: 시나리오 사이에 상태(HP·상태이상·잔존 오브젝트) 리셋,
  아레나를 실제 씬 오브젝트와 겹치지 않는 위치에
- **리팩터 전에 기준값을 확보한다** — 하네스 숫자가 곧 회귀 테이블이다.
  판별력 있는 시나리오를 설계한다 (직선이면 반드시 빗나가고 유도만 맞는 배치처럼,
  결과 숫자 하나로 동작 차이가 갈리는 구성)
- **자동 조작이 회피를 안 하면 밸런스 실측 전체가 무효다** — 「가만히 서서 맞는 봇」의
  생존 시간은 밸런스가 아니다. 회피 행동을 넣거나, 밸런스가 아닌 «경로» 검증으로만 쓴다

### 리포트에는 판정에 필요한 상태를 전부 넣는다

「킬 0」만 있으면 원인이 열 갈래다 — 적이 스폰됐나 · 스킬이 붙었나 · 팀이 맞나 ·
테이블이 로드됐나를 같은 리포트에 찍는다.
[사고] 킬 0 하나만 보고 원인을 세 번 잘못 짚었다. 진단 항목을 넣자 한 번에 잡혔다.

### 생존이 필요 없는 측정은 무적으로 잰다

「피해가 들어가는가」와 「생존 가능한가」는 다른 질문이다. 섞으면 둘 다 못 잰다.
[사고] 플레이어가 3초 만에 죽어 「킬 0」이 나왔는데 원인이 피해 경로인지 밸런스인지 안 갈렸다.
**경로 검증은 무적으로, 밸런스는 별도 시나리오로.** 리포트에 어느 쪽인지 명시한다.

### 하네스는 게임과 같이 늙는다

[사고] 시스템을 갈아엎었는데 하네스가 **옛 콘텐츠 id** 를 하드코딩하고 있어
게임은 멀쩡한데 하네스만 0을 보고했다.
**막기**: 콘텐츠 id 를 바꾸는 작업의 완료 조건에 하네스 갱신을 포함한다. 참조 id 는 한곳에 모은다.

## 에디터를 스스로 돌리는 두 경로

에디터 조작·컴파일 확인·플레이 검증은 직접 한다. **가는 길이 다르면 얻는 것도 다르다.**
어느 쪽인지 먼저 확정하고 시작한다.

| | A. 에디터 브리지 (MCP 등) | B. 배치모드 CLI |
|---|---|---|
| 조건 | 브리지가 붙어 있을 때 | 언제나 |
| 할 수 있는 것 | 씬 조작 · 플레이 · **화면 캡처** · 콘솔 직독 | 컴파일 · 에셋 빌드 · 헤드리스 플레이 |
| 못 하는 것 | — | **화면을 못 본다** (헤드리스라 캡처가 비어 나온다) |
| 쓰는 때 | 아트·연출·UI 처럼 **눈으로 봐야** 하는 것 | 로직·데이터·회귀 검증 |

**B 로는 룩을 판정할 수 없다.** 「컴파일 되고 루프가 돈다」와 「보기에 맞다」는 다른 주장이다.

### 에디터 프로세스는 분리해서 띄운다

[사고] 자동화 셸의 **자식 프로세스로** 에디터를 띄웠더니, 그 셸 작업이 끝나는 순간
에디터가 같이 죽었다. 다음 단계에서 「에디터가 없다」로 실패하고 원인이 안 보인다.
**막기**: 부모와 수명을 끊는 방식으로 띄운다. 띄운 뒤 **프로세스 목록에서 프로젝트 경로로 확인**한다 —
다른 프로젝트가 열려 있는 걸 우리 것으로 착각하기 쉽다.

**유니티 프로세스를 필터 없이 죽이지 않는다.** 남의 작업을 닫는다. 프로젝트 경로로 좁힌다.

### 브리지는 세션 시작 시점에 묶인다

[사고] 자동화 세션을 먼저 켜고 에디터를 나중에 켰더니 브리지가 끝내 안 붙었다.
연결이 **세션 개시 때 한 번** 맺어지는 구조라 뒤늦게 떠도 소용이 없다.
**막기**: 눈으로 봐야 하는 작업이면 **에디터를 먼저 띄우고** 자동화 세션을 시작한다.
붙지 않았으면 B 로 내려가되, **무엇이 막혔는지 보고**하고 룩 판정은 보류한다.

### 배치모드 검증 파이프라인

두 단계로 나눈다. 섞으면 실패 원인이 안 갈린다.

1. **컴파일 + 에셋 빌드** — 진입점 정적 메서드 하나를 실행시키고 끝낸다.
   로그에서 컴파일 에러만 먼저 훑는다. 에러가 있으면 2단계로 가지 않는다
2. **플레이 검증** — 요청 파일을 만들고 에디터를 띄우면 하네스가 스스로 플레이에 들어간다.
   리포트 파일이 생기면 읽고 프로세스를 정리한다

- **에디터가 그 프로젝트를 열어 두면 배치모드가 실패한다** (같은 프로젝트를 두 인스턴스가 못 연다).
  닫기 전에 **저장 안 된 작업이 날아갈 수 있다는 것을 먼저 알린다**
- 배치모드는 모달 다이얼로그를 안 띄운다 — 씬 백업 복구 창이 자동화를 막지 않는다
- 로그는 **프로젝트별로 분리해서 받는다** ([사고] 남의 임포트 로그를 우리 것으로 읽었다)
- [사고] 강제 종료를 반복하면 복구 다이얼로그가 에디터를 막는다 — 정상 종료 경로를 쓴다
- [사고] 측정이 도는 동안 스크립트를 고치면 도메인 리로드로 **그 측정이 통째로 날아간다**.
  하네스가 도는 동안은 코드를 건드리지 않는다

## 하네스가 쓰는 코드는 재생 밖에서도 서야 한다

에디터 스크립트가 런타임 전용 싱글턴을 참조하면, 재생 밖에서 도는 검증이 널로 죽는다.
**검증에 필요한 조회는 재생 여부와 무관하게 서는 정적 경로**로 뽑아 둔다.
