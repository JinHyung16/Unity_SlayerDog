# UnityGameDev — Unity 게임 개발 오케스트레이션

## 이 폴더가 무엇인가

**Unity 게임을 처음부터 만드는 범용 개발 오케스트레이션 문서 세트**다.
특정 타이틀·특정 장르에 종속되지 않는다 — **어떤 게임을 만들 때도 그대로 쓴다.**

**여기에는 심판할 원본이 없다.** 옮겨 오는 작업이라면 「원본과 같은가」로 끝나지만,
새로 만들 때는 그 기준이 없다. 그래서 심판을 **직접 만든다**:

1. **확정표가 심판이다** — 착수 13행에 없는 것은 만들지 않고, 확정표와 다르면 구현이 틀린 것이다
2. **실측이 완료 조건이다** — 「구현했다」가 아니라 「돌려서 쟀다」가 완료다

확정표가 애매해서 판정이 안 되면 그건 구현 문제가 아니라 **확정 문제**다. PD로 되돌린다.

## 뼈대 — 착수 13행이 트렁크 전체를 잠근다

```
      [착수 질문 13행]                      ← 가지: 사람에게만 물을 수 있는 것
             ▼
  확정표 · 코어루프 · 레퍼런스 실측본        ← 허리: 표준 산출물 «계약»
             ▼
 ┌───────────┴───────────┐
 │  규약 6 — 확정표가 값을 채운다        │  ← 트렁크: 게임 종류를 모른다
 │  View · Platform · Optimize          │
 │  DataFramework · UIFramework · Prefab│
 └───────────┬───────────┘
             ▼
   버티컬 슬라이스 → [계약 확정] → 트랙 겹치기 → 연결 → 실측 → 게이트 → QA
                                    ├ 기획 데이터
                                    ├ 클라 기능
                                    └ 아트/UI 프리팹·배치
             ▼
          Unity 빌드
```

**트랙은 겹치되 이음매는 나누지 않는다.** 계약(데이터 스키마 · 바인딩 계약)을 먼저 못 박으면
마지막이 「연결」로 끝나고, 계약 없이 겹치면 그게 재작업이다 — 규격은 `PD.md` 「트랙」 절.

**불변 조항 — 규약 문서에 특정 장르·특정 게임의 분기를 넣지 않는다.**
「서바이버면 이렇게」가 `UIFramework.md` 에 스며드는 순간, 새 장르가 올 때마다 규약을
전부 고치게 된다. 장르 차이가 나타나도 되는 자리는 딱 셋이다 —
① `장르사전.md` ② 레퍼런스 TSV(그 게임에서 **잰** 값) ③ 확정표의 «값».

**규약은 모양을 정하고, 확정표는 값을 정한다.** 규약이 값을 들고 있으면 그건 버그다.

## 이 세트가 다루는 축은 일곱이다

여섯 규약 + 장르. 이 일곱이 안 정해지면 **만든 것을 반드시 두 번 만든다.**

| 축 | 문서 | 안 정하면 |
|---|---|---|
| **장르** | `장르사전.md` | 그 장르가 이미 치른 수업료를 다시 낸다 |
| **뷰(카메라)** | `View.md` | 좌표계·정렬·스폰 경계·아트 규격이 전부 흔들린다 |
| **플랫폼** | `Platform.md` | 입력 계층과 UI 를 두 번 만든다 |
| **최적화** | `Optimize.md` | 최적화가 「나중에」로 밀리고, 그 나중은 갈아엎기다 |
| **데이터 구조** | `DataFramework.md` | 콘텐츠 추가마다 C# 을 고치게 된다 |
| **UI 구조** | `UIFramework.md` | 화면이 늘 때마다 깊이·로드·해제가 매번 다르게 난다 |
| **프리팹 구조** | `PrefabRule.md` | 프리팹이 MB 로 붓고, 한 화면 열면 전부 올라온다 |

## 오케스트레이션 — 기획이 들어오면 이 순서로 흐른다

사용자가 「이런 게임 만들어줘」를 넣으면 아래가 한 줄기로 흐른다.
**앞 단계의 산출물이 뒤 단계의 입력**이고, 건너뛰면 뒤에서 두 번 만든다.

```
사용자 기획
   │
   ▼
① 착수 확정표 13행            PD.md            ← 답을 받기 전엔 아무것도 안 만든다
   │
   ▼
② 레퍼런스 학습 → TSV         레퍼런스분석.md   ← 밸런싱·게임형식을 «잰다»
   │                                             design/view/client/ui/art.tsv
   │                                             curve_*.tsv (성장·스폰 곡선)
   ▼
③ UI/UX 배치                  UIFramework.md   ← ui.tsv 의 화면 종류·정보량·밴드를 받는다
   │                          + Design.md        (정보 우선순위)
   ▼
④ 시스템 · 콘텐츠 제작        DataFramework.md ← curve_*.tsv 를 데이터 모듈로 «굽는다»
                              + Client.md        View.md · Art.md · PrefabRule.md 가
                              + Design.md        각자 자기 축을 확정
```

**②의 TSV 가 이 흐름의 허리다.** 여기가 비면 ③·④가 「대체로 이런 장르는…」으로 시작한다.
그건 분석이 아니라 상식이고, 상식은 `장르사전.md` 에 이미 있다.

레퍼런스 게임이 없으면 ②를 건너뛰고 ①의 확정표 값만으로 간다 —
**대신 그 값들은 전부 「가정」으로 원장에 적고**, 개발 중 룩·감 판정이 막히는 순간
`레퍼런스분석.md` 의 「개발 중 재료 요청」 절이 발동한다.

## 언제 여나

| 언제 | 무엇부터 |
|---|---|
| 새 게임·새 콘텐츠 개발 **착수** | [PD.md](PD.md). 착수 13행의 답을 받기 전에 **아무것도 만들지 않는다** |
| 만든 것이 **스펙대로 도는지 검증** | 같은 문서. PD 를 QA/게이트 역할로 연다 |
| 특정 파트 작업만 (수치·시스템·에셋) | 해당 역할 문서만 (`Design` · `Client` · `Art`) |
| **규약 하나만** 필요 (UI 한 화면 추가 등) | 해당 규약 문서만. 확정표를 다시 묻지 않는다 |
| **레퍼런스 게임이 있을 때** | `레퍼런스분석.md` — 다섯 시각으로 병렬 해부 → **TSV** |
| **낯선 장르** 착수 | `장르사전.md` 해당 절. 절이 없으면 레퍼런스 실측으로 **절을 먼저 쓴다** |
| **사고 발생** | `함정사전.md` 색인에서 증상으로 찾는다. 새 사고는 일반화해 추가 |
| 개발과 무관한 **단순 수정** | 이 스킬을 열지 않는다. 프로젝트 루트 `CLAUDE.md` 가 기본 규칙이다 |

### 사람은 「게임 개발」이라는 말을 쓰지 않는다

**어휘로 판정하지 않는다.** 같은 요청이 사람마다 다르게 온다 —

> 「이런 게임 **만들 수 있어?**」 · 「**뱀서류** 하나 뽑자」 · 「로비 화면 **붙여줘**」
> 「스킬 **10개 추가**」 · 「**쿼터뷰**로 갈까 탑다운으로 갈까」 · 「**모바일**로 낼 건데」

**공통점은 「무엇을 플레이하게 만든다」**는 것이다. 그러면 이 스킬이다.

## 구성

```
SKILL.md          이 문서 — 진입점 · 뼈대 · 로딩 규칙
PD.md             오케스트레이터 — 착수 13행 · 확정 · 배분 · 게이트 · 원장 · 최종 QA
│
├── 역할 (지식 + 실행. 각자 자기 문서의 규약대로 일한다)
│    ├── Design.md    기획 — 코어 루프 · 스펙 · 수치/밸런스 · 콘텐츠 축 · 네이밍
│    ├── Client.md    클라 — 부트 순서 · 수명주기 · 풀링 · 검증 하네스 · 에디터 자동화
│    └── Art.md       아트 — 에셋 규격 · 반입 절차 · 폴더링/어드레서블 · 씬 · VFX
│
├── 규약 (트렁크. 게임 종류를 모른다. 확정표가 값을 채운다)
│    ├── View.md            뷰/카메라 — 좌표계 · 정렬 · 스폰 경계 · 뷰별 규약
│    ├── Platform.md        플랫폼 — 입력 · 해상도 · 세이프에리어 · 빌드 설정 · 예산표
│    ├── Optimize.md        최적화 — 처음부터 넣는 것 / 재고 나서 하는 것 · 측정법
│    ├── DataFramework.md   데이터 — SSOT · 모듈 조립 · 굽기 · Registry
│    ├── UIFramework.md     UI — Window/Panel/Component 3계층 · 동적로드 · 풀링 · 밴드
│    └── PrefabRule.md      프리팹 — 골격만 남긴다 · 용량 예산 · 조립 단위 · 앵커
│
├── 지식
│    ├── 장르사전.md      장르별 문법 · 뷰/조작 관례 · 성능 특성 · 장르 고유 함정
│    ├── 함정사전.md      실제로 났던 사고와 막는 방법 (전 역할 공통)
│    └── 레퍼런스분석.md  착수 전 병렬 해부 — 재료 규약 · 네 시각 배분 · 병합 게이트
│
└── (레퍼런스는 폴더로 안 들고 있는다 — 그때그때 **잰 TSV**가 표본이다)
```

**프로젝트마다 새로 만드는 것은 셋뿐이다** — 확정표(착수 13행의 답) ·
`TASKS.md`(큐) · `docs/history/`(히스토리) · `docs/spec/`(현재 상태). **나머지는 프로젝트가 바뀌어도 그대로 쓴다.**

## 표본은 폴더가 아니라 «잰 값»이다

[사고] 한때 `_Reference/<장르>/` 에 「완성된 구조 예시」를 적어 두고 표본으로 삼았다.
그런데 그 안의 숫자는 **실제 게임에서 잰 것이 아니라 우리가 지어낸 것**이었다.
지어낸 표본은 상식과 구분이 안 되고, 상식은 `장르사전.md` 에 이미 있다.
그래서 참고할 때마다 「이 숫자가 어디서 왔지」를 아무도 답할 수 없었다.

표본은 **사용자가 지목한 실제 레퍼런스 게임에서 잰 TSV**다. 절차는 `레퍼런스분석.md`.
출처가 붙지 않은 수치는 표본이 아니라 추측이다.

## 역할이 곧 시각이다

같은 것을 봐도 역할마다 봐야 하는 것이 다르다. 역할을 연기할 때는 그 시각으로만 본다.

| 역할 | 「레벨업 3택1」을 볼 때 |
|---|---|
| PD | 이게 이번 슬라이스에 있어야 하나? 게이트 통과 조건이 숫자로 박혀 있나? |
| 기획 | 후보 풀 규칙이 표로 있나? 중복 허용? 가중치? 값은 데이터 파일에 있나? |
| 클라 | 일시정지 중 다른 시스템이 새나? 풀 재사용 시 상태가 남나? 하네스로 잡히나? |
| 아트 | 카드가 세이프에리어 안인가? 폰트에 글리프가 있나? 터치 타깃이 충분히 큰가? |

한 명이 전 역할을 연기한다. 역할을 바꿀 때는 **그 역할의 문서를 열고, 그 시각으로만 본다.**

## 문서 로딩 규칙 — 단계마다 여는 것만 연다

**전 문서를 상시 로드하지 않는다.** 한 번에 여는 것은 최대 3개다.

| 단계 | 여는 문서 |
|---|---|
| 착수 / 확정 | `PD.md` + `장르사전.md` 해당 절 |
| 레퍼런스 해부 | `레퍼런스분석.md` + 각 파트가 자기 역할 문서 |
| 뷰·카메라 결정 | `View.md` (+ 같은 뷰 레퍼런스의 `view.tsv`) |
| 플랫폼·예산 결정 | `Platform.md` |
| 데이터 설계 | `DataFramework.md` + `Design.md` |
| UI 설계·구현 | `UIFramework.md` + `PrefabRule.md` |
| 시스템 구현 | `Client.md` (+ `함정사전.md` 색인 훑기) |
| 에셋 작업 | `Art.md` |
| 성능이 목표를 못 맞춤 | `Optimize.md` |
| QA / 게이트 | `PD.md` 게이트 절 + 원장 |

## 표기 규약

| 마커 | 뜻 | 읽는 쪽이 할 일 |
|---|---|---|
| **`[예시]`** | 이렇게 생기면 된다는 **모양**. 값은 프로젝트마다 다르다 | 모양만 베끼고 값은 갈아끼운다 |
| **`[사고]`** | 실제로 났던 실패. 재발 조건이 그대로 남아 있다 | 같은 자리를 먼저 확인한다 |
| **`[확정표 N]`** | 착수 N행이 이 값을 정한다 | 확정표를 보고 채운다. 임의로 정하지 않는다 |
| 마커 없음 | 프로젝트 불변 규칙 | 그대로 지킨다 |

**코드 블록·경로·클래스명은 전부 `[예시]` 취급이다.** 프로젝트에 이미 규약이 있으면 그쪽이 우선한다.
수치가 붙은 문장은 `[예시]` 표시된 남의 실측이거나 **재는 방법**이어야 한다.

## 이 문서 세트에 적을 때의 금칙

**특정 타이틀의 고유명사·실측치를 규약 문서에 적지 않는다.**

| 금지 | 대신 |
|---|---|
| 게임 고유명사 (스킬명·캐릭터명·화면명) | 역할 이름 (`자동 발동 스킬` · `선택 카드` · `결과 화면`) |
| 특정 프로젝트의 실측치 | 재는 **방법**. 수치는 그 프로젝트의 원장에 |
| 특정 장르에만 통하는 규칙을 규약 문서에 | `장르사전.md` 의 해당 장르 절로 |
| 특정 프로젝트의 완성된 트리 | 그 프로젝트의 원장으로 |

**프로젝트 사정에 맞춰 이 문서들을 고치고 싶어지면,** 그건 대개 원장에 적을 회고다.
단, **어느 프로젝트에서도 재발할 사고**는 `함정사전.md` 에 일반화해 적는다.
