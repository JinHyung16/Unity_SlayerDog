# View — 뷰 · 카메라 · 좌표계 · 정렬

> [확정표 2] 가 이 문서의 값을 정한다. **뷰는 취향이 아니라 계약이다.**

## 뷰 하나가 잠그는 것 — 이래서 2번째로 묻는다

뷰를 바꾸면 아래가 **전부** 다시다. 그래서 코어 루프보다 먼저 확정한다.

```
뷰 결정
 ├─ 좌표계      어느 평면이 「바닥」인가 (XZ? XY?) · 높이 축은 무엇인가
 ├─ 정렬        무엇이 앞에 그려지나 (Z? Y? sortingOrder? depth buffer?)
 ├─ 입력 사상   화면 좌표 → 월드 좌표 변환 규칙 (레이? 평면 교차? 그대로?)
 ├─ 스폰 경계   「화면 밖 바로 바깥」이 기하학적으로 어디인가
 ├─ 컬링/제거   무엇을 「안 보인다」고 판정하나
 ├─ 아트 규격   피벗 위치 · 스프라이트 각도 · 그림자 처리 · PPU
 └─ UI 월드앵커 HP바·피해 숫자가 월드의 어느 점을 따라가나
```

**「일단 만들고 나중에 카메라 정하죠」는 위 일곱을 전부 두 번 만들겠다는 말이다.**

## 확정해야 하는 5가지 — 「탑다운」 한 단어로는 부족하다

| # | 항목 | 선택지 | 이게 갈리면 |
|---|---|---|---|
| 1 | **차원** | 2D 스프라이트 / 3D 메시 / 2.5D(3D 월드 + 2D 캐릭터) | 정렬 방식과 아트 파이프라인 전체 |
| 2 | **투영** | Orthographic / Perspective | 원근 왜곡 · 화면 경계 계산 · 줌 의미 |
| 3 | **각도** | 탑다운(90°) / 쿼터뷰(30~60°) / 사이드(0°) / 자유 | 가시 영역 모양 · 아트 피벗 |
| 4 | **카메라 자유도** | 고정 / 추적만 / 팬·줌 / 회전까지 | 입력 계층 · 스폰 경계 재계산 주기 |
| 5 | **기준 평면** | XZ(3D 관례) / XY(2D 관례) | 모든 벡터 연산과 물리 |

**5번이 제일 많이 사고 난다.** 2D 게임인데 XZ 평면을 쓰는 구성(3D 물리를 쓰려고)도,
3D 게임인데 XY 를 쓰는 구성도 정당하다. **정당하지만 한 프로젝트에 둘이 섞이면 끝난다.**
확정표에 **한 줄로 못 박고**, 그 뒤로는 「이 프로젝트의 바닥은 XZ」가 불변 규칙이다.

## 뷰별 규약

### 탑다운 (90°, 위에서 수직)

- **가시 영역이 직사각형**이다 — 유일하게 스폰 경계 계산이 쉬운 뷰
- 정렬: 겹침이 거의 없다. 2D면 레이어 밴드(바닥/그림자/유닛/이펙트/UI)로 충분
- 아트: 캐릭터를 위에서 본 그림이어야 한다. **옆모습 스프라이트를 90° 탑다운에 쓰면
  전부 누워 보인다** — 「탑다운인데 캐릭터는 정면」은 사실 아래의 «유사 탑다운»이다
- 입력: 화면 좌표 → 바닥 평면이 1:1. 가장 단순

### 유사 탑다운 (75~85°, 캐릭터는 정면을 보는 2D)

- 서바이버·핵앤슬래시 2D 의 실제 표준. **엄밀히는 탑다운이 아니다**
- 정렬: **Y 정렬**(아래에 있을수록 앞) 이 필수. 없으면 캐릭터가 서로를 뚫고 지나간다
- 바닥 타일은 별도 밴드로 내려 Y 정렬에서 제외한다 (타일이 캐릭터를 가린다)
- 그림자는 **발밑 타원 스프라이트**가 정답. 실 그림자는 이 각도에서 안 보인다

### 쿼터뷰 / 아이소메트릭 (30~60° 기울임)

- **가시 영역이 사다리꼴이다.** 이게 이 뷰의 모든 함정의 뿌리
  - [사고] 고정 반지름 «원형 링»으로 적을 스폰했더니 화면 위쪽에만 몰렸다.
    화면 위는 멀리 보이고 아래는 가까이 보이기 때문이다
  - **막기**: 방향별로 「화면을 벗어나는 거리」를 뷰포트 역변환으로 구해 그 경계를 쓴다 (아래 절)
- 정렬: 3D면 depth buffer 가 처리한다. 2D 아이소면 **깊이 = f(x, y)** 공식을 한 곳에 두고 전부 그걸 쓴다
- 아트: 피벗 = 발밑. 스프라이트는 이미 기울여 그려진 것이어야 한다 (billboard 로 세우면 각도가 안 맞는다)
- 입력: 화면 → 바닥 평면 **레이 교차**. 「마우스 위치 그대로」는 틀린다

### 사이드뷰 (0°, 옆에서)

- 중력·점프가 게임 문법이 된다 → 물리 통일(`장르사전.md` 액션 절)
- 정렬: Z 를 레이어로만 쓴다. 배경 패럴랙스가 별도 축
- 카메라 추적에 **데드존(카메라가 안 따라오는 사각형)** 과 **룩어헤드**가 필요 —
  플레이어를 화면 정중앙에 고정하면 진행 방향이 안 보인다

### 2.5D (3D 월드 + 빌보드 2D 캐릭터)

- **가장 함정이 많다.** 정렬이 depth buffer 와 sortingOrder 두 체계로 갈린다
- 반투명 스프라이트는 depth 를 안 쓴다 → 3D 지형과의 앞뒤가 깨진다.
  **결정**: 캐릭터를 불투명 컷아웃(alpha clip)으로 갈 것인가, 렌더 순서를 수동 관리할 것인가
- 빌보드 회전축: Y 만 도는가(기울임 유지) 카메라를 완전히 마주보는가 — **한 곳에서만 구현**

### 1인칭 / 3인칭 자유 카메라

- 카메라 충돌(벽 뚫림)·FOV·감도가 **스펙 항목**이다. 「적당히」는 판정 불가
- UI 는 월드 스페이스와 스크린 스페이스가 섞인다 → 밴드 설계에 월드 UI 밴드를 하나 더 둔다
- 멀미(모션 시크니스)는 성능이 아니라 설계 문제 — 카메라 가속·흔들림에 상한을 스펙으로

## 화면 경계는 «계산»이 아니라 «실측»이다

스폰·컬링·UI 여백이 전부 이 경계 위에 선다. **추측한 반지름을 상수로 박지 않는다.**

### 구하는 법 — 뷰포트 역변환

```
[예시] 원리 (뷰 종류 불문)
1. 뷰포트 좌표(0..1)의 네 모서리 + 필요한 방향들을 잡는다
2. 카메라에서 그 방향으로 «바닥 평면»과 교차시킨다 (Orthographic 도 동일)
3. 나온 월드 점들이 «화면에 보이는 바닥 영역»이다
4. 스폰은 그 영역을 바깥으로 M 유닛 밀어낸 테두리에서 한다
```

- 이 계산은 **카메라 파라미터가 바뀔 때만** 다시 한다 (매 프레임 금지) —
  줌·화면 회전·해상도 변경 시 무효화하고 재계산하는 훅을 둔다
- **경계를 시각화하는 디버그 그리기를 처음부터 넣는다.** 눈으로 못 보는 경계는 반드시 틀린다
  (G9 게이트의 증거물이 이 그림이다)

### 화면 밖 제거는 «화면 밖 AND 거리 초과»

거리 단독으로 지우면 **먼 쪽(화면 위)에 보이는 것을 눈앞에서 지운다.**
화면 밖 단독으로 지우면 카메라가 되돌아왔을 때 있어야 할 것이 없다.
둘 다 만족할 때만 회수한다.

## 좌표계 규약 — 한 프로젝트에 하나

확정표에서 정한 기준 평면을 **유틸 한 곳**으로 강제한다. 각자가 `new Vector3(x, 0, z)` 를
직접 쓰기 시작하면 평면이 섞이는 것을 아무도 못 잡는다.

```
[예시] XZ 평면 프로젝트의 규약
- 월드 위치       : Vector3 (y 는 높이, 게임플레이 로직은 y 를 보지 않는다)
- 게임플레이 좌표 : Vector2 (x, z) — 거리·방향·판정은 전부 여기서
- 변환은 유틸에서만: ToPlane(Vector3) / ToWorld(Vector2, height)
- 회전            : 바닥 평면 위의 각도 하나(도). 쿼터니언은 표현용으로만
```

- **충돌·거리 판정을 평면에서 한다** — 높이 축을 섞으면 계단·경사에서 사거리가 달라진다
- 물리 엔진을 쓰지 않고 자작 판정을 쓸 때는 판정 도형을 **평면 2D 도형**으로 정의한다
  (원 vs OBB 등). 3D 콜라이더와 자작 판정이 공존하면 어느 쪽이 진실인지부터 정한다

## 정렬 — 「무엇이 앞에 그려지나」를 한 곳에서 정한다

정렬 규칙이 코드 여러 곳에 흩어지면 **새 오브젝트 종류가 생길 때마다 앞뒤가 깨진다.**

```
[예시] 밴드 테이블 — 이 표가 정렬의 유일한 출처
밴드         범위          Y정렬   내용
Ground       -1000         X       바닥 타일 · 데칼
Shadow        -500         X       발밑 그림자
Unit             0         O       플레이어 · 적 · NPC
Projectile     100         O       투사체 · 드랍
FxOver         500         X       상위 이펙트 · 피격 연출
WorldUI       1000         X       HP바 · 피해 숫자
```

- **Y 정렬 대상과 비대상을 표에 명시**한다. 섞으면 그림자가 캐릭터 위로 올라온다
- 밴드 값은 상수 클래스 하나에 모은다. 매직 넘버로 흩어지면 두 종류가 같은 값을 문다
- 3D 는 depth buffer 가 하지만, **반투명·파티클·UI 는 여전히 수동 밴드**가 필요하다

## 카메라 리그 — 추적·흔들림·줌은 «따로» 산다

한 컴포넌트가 추적도 하고 흔들기도 하면, 흔들림이 추적 위치를 덮어써서 카메라가 튄다.

```
[예시] 계층
CameraRig            추적 (타깃 따라감, 데드존·스무딩·경계 클램프)
└ ShakeOffset        흔들림 (로컬 오프셋만. 리그 위치를 안 건드린다)
  └ Camera           투영·FOV·줌
```

- 스무딩은 **unscaledDeltaTime** 여부를 정한다 — 일시정지 중 카메라가 계속 움직이면 안 된다
- 맵 경계 클램프는 **가시 영역 크기**를 알아야 한다 → 위 「화면 경계」 계산과 같은 출처를 쓴다
- 흔들림 상한을 스펙으로 받는다. 「타격감」이라는 말로 무제한 흔들면 멀미가 난다

## 월드 → UI — 피해 숫자 · HP바

- **카메라 각도 확정 후에** 붙인다. 각도가 바뀌면 앵커 오프셋이 전부 어긋난다
- 월드 좌표 → 스크린 좌표 변환은 **카메라 뒤에 있는 점**을 반드시 걸러낸다 (뒤로 가면 좌표가 뒤집힌다)
- 대량 표시(피해 숫자)는 **풀링 + 상한**이 전제. 상한 도달 시 동작(가장 오래된 것 회수)을 스펙으로
- 빌보드가 필요한 월드 UI 는 회전 규칙을 카메라 리그와 같은 규칙으로 (위 2.5D 절)

## 완료 체크리스트

- [ ] 확정표 2행의 5항목(차원·투영·각도·자유도·기준 평면)이 전부 한 줄로 적혀 있다
- [ ] 기준 평면 변환이 **유틸 한 곳**에만 있다 (직접 `Vector3` 조립 grep → 유틸 밖 0건)
- [ ] 화면 경계를 뷰포트 역변환으로 구하고, **디버그로 그려서 눈으로 봤다**
- [ ] 스폰이 그 경계 기준이다 (고정 반지름 상수 0건)
- [ ] 제거 판정이 「화면 밖 AND 거리 초과」다
- [ ] 정렬 밴드 표가 있고 상수가 한 곳에 모여 있다
- [ ] 카메라 리그에서 추적·흔들림·줌이 분리돼 있다
- [ ] **확정 카메라 각도에서 찍은 실제 플레이 스크린샷**이 원장에 있다 (씬뷰 확인은 확인이 아니다)

## 함정 (요약 — 상세는 `함정사전.md`)

| 증상 | 원인 |
|---|---|
| 적이 화면 위쪽에만 몰림 | 기울인 카메라 + 원형 스폰 링 |
| 캐릭터가 서로를 뚫고 지나가 보임 | Y 정렬 없음 (유사 탑다운) |
| 바닥 타일이 캐릭터를 가림 | 타일이 Y 정렬 대상에 포함됨 |
| 눈앞의 적이 갑자기 사라짐 | 거리 단독 제거 판정 |
| 스프라이트가 다 누워 보임 | 옆모습 아트를 90° 탑다운에 사용 |
| 캐릭터가 3D 지형에 파묻히거나 뜸 | 2.5D 반투명 스프라이트 + depth buffer |
| 카메라가 미세하게 튐 | 추적과 흔들림이 같은 트랜스폼을 씀 |
| 일시정지인데 카메라가 움직임 | 스무딩이 `deltaTime` 대신 `unscaledDeltaTime` (또는 반대) |
