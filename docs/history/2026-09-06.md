# 2026-09-06 — 로비 재편 · 스킬 모듈화 · 아트 재작업

## 확정
- **「런타임에 숨긴 것」과 「없앤 것」은 다르다.** 프리팹을 실제로 비운다
- 탭은 4개 — 시작 · 캐릭터 · 스킬 트리 · 설정.
  영웅(고르기)과 도감(모아보기)이 같은 화면이었다. 같은 것을 두 군데서 보여주면 둘 다 흐려진다
- **한 폴더 = 한 스킬.** 목적 한 줄: Ctrl+C / Ctrl+V 로 스킬 하나가 뚝딱 나오는 것
- **공유를 버린다.** 공유는 남의 스킬을 건드릴까 봐 못 고치게 만든다. 복붙이 목적이면 공유보다 복제다
- 이펙트 방향: **외곽만 따서 실루엣으로 승부한다.** 스킬 이름이 그림 한 장으로 읽혀야 한다
- **개는 이족보행이다.** 네 발이 「진짜 개」 실루엣에 가깝지만, 이 게임의 개는 원반을 던지고 슬리퍼를 집어 던지는
  — 손으로 뭔가를 하는 캐릭터다

### 스킬 모듈화 (ActionScriptKit 참고)
트리거/비헤이버 분리와 데이터 조립은 이미 같은 사상이었다. 실제로 빠져 있던 둘만 가져왔다.
- `[BTNode(ESkillNodeType.…)]` 어트리뷰트 + `BTNodeRegistry` 리플렉션 수집 → `BTBuilder` switch 60줄 제거.
  전에는 세 군데를 고쳐야 했고 switch 를 빠뜨려도 **컴파일은 통과하고 런타임에 조용히 아무 일도 안 했다**
- 어트리뷰트에 `Inert = new[]{ … }` — **받는 것 ≠ 동작하는 것**을 구분한다
- 데이터 폴더를 킷 규약에 정렬. 파츠 27 ↔ 스킬 27 **1:1**, 옵션 159 전부 파츠 하나에 귀속인데
  **186개 파일이 자기 스킬에서 떨어져** 있었다
- `config.json` 에 `folderOnly: true` — 제네릭 스캔이 같은 폴더의 `skill.js` 까지 파츠로 집는 것을 막는다
- id 표 검사 순서 교정 — 폴더 것을 합친 **뒤에** 돈다. **검사를 건너뛴 데이터는 검사가 없는 것보다 나쁘다**

### 최종 데이터 레이아웃 (Master / Method / Visual)
```
GameData/Skill/
  Master/  bark_cone.js      「이 스킬 = Method + Visual」 조합 + 트리거 + 슬롯   (27)
  Method/  instant.js …      발사 방식. 공용                                      (9)
  Visual/  bark_cone.js      이미지 키 · 색 · 수치 · 레벨 곡선                     (27)
  Part/    bark_cone.js      착용 파츠                                            (27)
  Option/  bark_cone_area.js 파츠 옵션                                            (159)
```
- 폴더 이름에서 숫자 접두를 뗐다. `id: 2002` 는 데이터 안에 남는다
- `launch` → `method` 개명. `stat` 을 `Visual` 로 합쳤다 — 토큰 이름만 둘로 남긴 이유는
  수치와 그림이 **읽는 사람에게** 다른 것이기 때문
- **Master 는 Visual 을 이름으로 가리키지 않는다. 파일 이름이 곧 연결이다.** 어긋나면 조용히 남의 그림이 나간다
- Method 만 이름으로 가리킨다 — 발사 방식은 재사용이 본질이라 9종을 27개가 나눠 쓴다

## 발견
- **「그린 것 ≠ 보이는 것」의 원인 셋이 겹쳐 있었다** (함정 43)
  1. `Art2DBuilder` 가 FX 프리팹을 20fps·반복 없음으로 구워 5프레임이면 0.25초에 끝나고 정지
  2. 그 정지 프레임이 페이드로 **알파 0** 이었다 — 연출이 끝나면 아무것도 없었다
  3. `SkillVisual.Play()` 가 **ParticleSystem 만** 돌리는데 이 프로젝트 FX 에는 파티클이 하나도 없다.
     전부 스프라이트 프레임 애니였고, 애니는 풀에서 꺼내질 때 `OnEnable` 되감기에만 의존했다.
     `SpriteAnimator` 는 이미 있었다 — 만들 것이 아니라 **연결할 것**이었다
- **걷기가 미끄러져 보인 이유**: 몸통 상하 이동이 1픽셀이었고, 4장 중 1·3번 프레임이 완전히 같아 실제 포즈는 셋뿐이었다.
  픽셀 걷기에서 몸이 위아래로 뛰는 것은 장식이 아니라 걷는다는 **주된 단서**다
- **접지 그림자가 없던 것**이 탑다운에서 「떠 보임」의 주범이었다. 가장 싸고 효과가 크다
- **외곽선이 그림을 잡아먹고 있었다.** `fin()` 이 레이어마다 2px 선을 씌우고 그걸 쌓아 겹치는 자리마다 누적됐다
- 왈왈·으르렁이 검은 덩어리로 보인 원인: `render()` 가 속 찬 모양에도 안쪽을 깎고 있었다.
  만화형은 **바깥으로 둘러야** 밝은 면이 통째로 남는다
- 속 비우기가 내부 디테일을 먹었다 → **구멍**을 뚫으면 침식이 구멍 둘레에도 선을 만든다(공짜 디테일).
  단 구멍은 디테일을 더하는 도구지 형태를 바꾸는 도구가 아니다 (슬리퍼가 띠 셋, 눈이 아령, 폭발이 톱니바퀴가 됐다)
- 가는 꼬리를 가로 막대로 그려 **뒤로 뻗은 팔**로 보였다. 굵기가 일정한 수평 막대는 팔다리의 그림이다
- **확인 질문 두 개를 한 문단에 묶어 던져 놓고 짧은 답을 둘 다에 대한 승낙으로 해석했다.**
  「나무만」이었는데 네 발까지 바꿨다. 서로 다른 판단이 필요한 것은 따로 묻는다
- 컴파일 직후 첫 검증에서 `MethodPath` 가 빈 값 — **옛 어셈블리가 새 JSON 을 읽은 것**.
  필드 이름을 바꾼 직후의 첫 실행은 이 착시를 조심한다
